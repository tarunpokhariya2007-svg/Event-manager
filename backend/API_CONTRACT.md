## 1. Conventions

| Topic | Rule |
|---|---|
| Dates | `"YYYY-MM-DD"`, validated (month lengths, leap years). No time zones; all dates are local calendar dates. |
| Clock times in **responses** | `"HH:mm"`, 24-hour. Minute 1440 (end of day) is written `"24:00"`. |
| Clock times in **requests** | Integer minutes since midnight, in fields ending `_min` (`start_min`, `end_min`, `deadline_min`, …). Range 0–1440. |
| Durations / buffers | Integer minutes (`duration_min`, `buffer_min`). |
| Priority | Integer `1`–`5` (5 = highest) on tasks, events and timeline rows. ⚠ ASSUMED range/representation. |
| IDs | Either a **string** (1–64 chars of `A-Z a-z 0-9 - _ : .`) or a **non-negative integer** ≤ 2^53−1. The backend echoes each id with the JSON type it arrived in. An unassigned id is `null`. **Numeric `7` and string `"7"` are different ids** and may coexist (see §1.1). Applies to task ids, event ids, `prerequisite_ids`, `reference_id`, `task_id`, `event_a_id`, `event_b_id`. |
| Row ids generated by the engine | Timeline `"tl-N"`, slots `"slot-N"`, conflicts `"cf-N"` (N starts at 1 per response). |
| Optional fields | Accepted when missing or `null`. In responses an unset optional field is always present and `null` (keys never disappear). |
| Midnight | Events and tasks cannot cross midnight (`start_min < end_min` within one day). |
| Unknown request fields | Ignored. |
| CORS | `Access-Control-Allow-Origin` comes from `CHRONOPLAN_CORS_ORIGIN` (default `*`). **`*` is for local development only**; set the frontend's exact origin when deployed. |

### 1.1 ID representation (Phase 2)

**In JSON bodies and responses** an id keeps its JSON type: `7` (number) or `"7"` (string). Both are valid and distinct.

**In SQLite** every id is stored as a pair `id_type` (`'number'` | `'string'`) + `id_value` (canonical text), forming the composite primary key. Dependencies use the same pair for both ends, with composite foreign keys, so `7` and `"7"` can never collide.

**In URL path segments** (`/tasks/<id>`, `/events/<id>`, `/tasks/<id>/dependencies/<prerequisite_id>`):

| Segment | Meaning |
|---|---|
| `7` | numeric id 7 (a canonical non-negative integer: digits only, no leading zeros) |
| `%227%22` (i.e. `"7"` URL-encoded) | **string** id `"7"` |
| `abc`, `task-1`, `007` | string ids (anything that is not a canonical integer is a string) |

Rule: a segment starting with `"` is parsed as a JSON string literal; otherwise a canonical integer is numeric; otherwise the text is a string id. Percent-encoding is decoded first. An invalid id in a URL is `400 validation_error`.

**Server-assigned ids:** when `id` is omitted on `POST /tasks` or `POST /events`, the server assigns the next **numeric** id (`max numeric id of that table + 1`, starting at 1). String ids never influence assignment.

## 2. Errors

Every error uses one shape:

```json
{ "error": { "code": "validation_error", "message": "task duration_min must be between 1 and 1440" } }
```

| HTTP | `code` | When |
|---|---|---|
| 400 | `invalid_json` | Body is not parseable JSON. |
| 400 | `validation_error` | JSON is valid but a field is missing, mistyped or out of range. `message` names the field. |
| 404 | `not_found` | Unknown resource id. |
| 405 | `method_not_allowed` | Route exists but not for this method (JSON body, as of Phase 2). |
| 409 | `circular_dependency` | A dependency edge would create a cycle, **or** an optimize request's tasks contain a dependency cycle. |
| 409 | `conflict` | Request conflicts with stored state (e.g. duplicate id). |
| 500 | `internal_error` | Unexpected server fault, including a generated schedule that failed independent validation (should never happen; details go to the server log). The message never contains internals (no SQL, no paths). |
| 503 | `database_unavailable` | SQLite is busy/locked/unreadable right now. Retry later. |

Success codes: `200` read/update/compute, `201` created, `204` deleted (no body).

Unknown URLs return `404 not_found` and wrong methods return `405 method_not_allowed`, both in the JSON shape above. Malformed JSON bodies return `400 invalid_json`. Model-level problems (missing field, out of range, bad date, bad id) are `400 validation_error` (the Phase 1 convention is kept; `422` is not used).

> **Infeasible schedules are not errors.** An optimize request that cannot place everything returns `200` with `status` `"partial"` or `"infeasible"` and populated `unscheduled_tasks`. `400` is reserved for malformed input.

**Result (top level)**
| Field | Type |
|---|---|
| `target_date` | date |
| `status` | enum (§3) |
| `solver_duration_ms` | number |
| `total_allocated_min` | integer |
| `total_available_min` | integer |
| `timeline` | array of Timeline entry |

**Timeline entry:** `id` (string `"tl-N"`), `type` (enum), `reference_id` (id of the event/task), `title`, `start` (`HH:mm`), `end` (`HH:mm`), `duration_min` (int), `priority` (int 1–5), `status` (enum), `explanation` (string – why it was placed here); **new:** `date` (the row's date), `session_index` / `session_count` (1-based session of a task and the number of sessions; `null` for events). **Slot:** `id` (`"slot-N"`), `start`, `end` (`HH:mm`), `duration_min`, `label` (string), **new:** `date`. Free time left inside the availability windows after placement.

**Unscheduled task:** `task_id` (id), `title`, `reason` (string), `suggested_action` (string), plus extras `remaining_min` (int) and **new** `reason_code` (stable machine-readable string, list in PHASE4_DESIGN.md §11).

**At-risk task:** `task_id` (id), `title`, `risk_level` (enum), `buffer_min` (int; available − required, negative = shortfall), `reason` (string), plus extras `required_min`, `available_min` (int) and **new** `category` (`deadline_risk` \| `hard_infeasible` \| `dependency_blocked` \| `insufficient_capacity`), `deadline` and `estimated_completion` (`"YYYY-MM-DDTHH:mm"`, `24:00` = end of day; `null` when none).

**Conflict:** `id` (`"cf-N"`), `event_a_id`, `event_b_id` (ids), `date`, `overlap_start`, `overlap_end` (`HH:mm`), `message`. ⚠ The conflict shape is a backend proposal; the frontend's version has not been seen.

### ✅ `POST /api/v1/schedule/optimize`  (Phase 4 scheduling engine — a read-only **preview**)

Generates a proposed schedule. It **never modifies** tasks, events or dependencies. There is no apply endpoint in
Phase 4 (see PHASE4_DESIGN.md §14).

**Data source.** `"data_source": "request"` (default): tasks come from `flexible_tasks`, events from `fixed_events`; the database is not read.
`"data_source": "database"`: every stored task (with its stored prerequisites) and every stored event inside the horizon are loaded once;
`flexible_tasks` / `fixed_events` must then be absent or empty (`400` otherwise).

**Rules.** Every task `prerequisite_ids` entry must be a task in the same list (`400` otherwise). A dependency cycle among the tasks → `409 circular_dependency`.
Tasks without an `id` get the next numeric id. Completed/cancelled tasks (see §3) are never placed. Events outside the horizon are ignored; overlapping events are returned in `conflicts` and never moved.
Task `earliest_start_min` / `latest_completion_min` are times of day applied to every day; a deadline is `deadline_min` of `deadline_date` (default `1440` = end of that day).
Infeasible schedules are **not** errors: `200` with `status` `"partial"`/`"infeasible"` and explained `unscheduled_tasks`.

### ✅ Tasks
| Method & path | Request | Success | Errors |
|---|---|---|---|
| `GET /api/v1/tasks` | – | `200` JSON array of Task (insertion order) | – |
| `POST /api/v1/tasks` | Task | `201` Task (with assigned `id`) | `400`, `409 conflict` (duplicate id of the same type) |
| `GET /api/v1/tasks/<id>` | – | `200` Task | `400` bad id, `404` |
| `PUT /api/v1/tasks/<id>` | Task | `200` Task | `400`, `404`, `409 circular_dependency` |
| `DELETE /api/v1/tasks/<id>` | – | `204` (no body) | `400`, `404` |

**PUT is a full replacement.** Every field not sent reverts to its default (optional fields become `null`, `priority` 3, `allow_split` true, `deadline_min` 1440, `min_chunk_min` `min(30, duration_min)`) and `prerequisite_ids` replaces the stored set. Send the complete object. `id` may be omitted in the body; if present it must equal the URL id *including its type* (`400` otherwise). The update is atomic: if any part fails (e.g. a cycle), nothing changes.

**DELETE** also removes every dependency row that mentions the task (as task or as prerequisite). Tasks that depended on it simply lose that prerequisite; they are not deleted.

Create a task:
```http
POST /api/v1/tasks
{ "title": "Write report", "duration_min": 120, "priority": 4,
  "deadline_date": "2026-11-05", "deadline_min": 1020, "prerequisite_ids": [1] }
```
```http
201 Created
{ "id": 2, "title": "Write report", "description": null, "technical_context": null,
  "priority": 4, "duration_min": 120, "min_chunk_min": 30, "allow_split": true,
  "deadline_date": "2026-11-05", "deadline_min": 1020, "earliest_start_min": null,
  "latest_completion_min": null, "prerequisite_ids": [1], "status": null }
```
Other examples: `GET /api/v1/tasks` → `200 [ Task, … ]`; `GET /api/v1/tasks/2` → `200 Task`; `PUT /api/v1/tasks/2` with a full Task → `200 Task`; `DELETE /api/v1/tasks/2` → `204`; `GET /api/v1/tasks/%227%22` → the task whose id is the **string** `"7"`.

Duplicate id → `409 { "error": { "code": "conflict", "message": "a task with id 7 already exists" } }`.

### ✅ Dependencies (per task)
| Method & path | Request | Success | Errors |
|---|---|---|---|
| `GET /api/v1/tasks/<id>/dependencies` | – | `200` array of Dependency (the task's prerequisites, insertion order) | `404` task |
| `POST /api/v1/tasks/<id>/dependencies` | `{ "prerequisite_id": id }` | `201` Dependency | `400` (missing/bad id, **self-dependency**), `404` (task or prerequisite unknown), `409 conflict` (duplicate), `409 circular_dependency` |
| `DELETE /api/v1/tasks/<id>/dependencies/<prerequisite_id>` | – | `204` | `404` (task unknown or no such dependency) |

`prerequisite_id` may be a number or a string (typed, see §1.1); the URL form of `<prerequisite_id>` follows the same rules as any id segment. Cycles are detected through the whole stored graph (direct, indirect and long chains); diamonds (`A→B`, `A→C`, `B→D`, `C→D`) are allowed. A rejected request changes nothing.

```http
POST /api/v1/tasks/3/dependencies        { "prerequisite_id": 2 }
201 Created                              { "task_id": 3, "prerequisite_id": 2 }

GET /api/v1/tasks/3/dependencies
200 OK                                   [ { "task_id": 3, "prerequisite_id": 2 } ]

DELETE /api/v1/tasks/3/dependencies/2
204 No Content
```

> The global `GET/POST /api/v1/dependencies` endpoints proposed in Phase 1 are **not** implemented; use the per-task endpoints above or `prerequisite_ids` on the task.
